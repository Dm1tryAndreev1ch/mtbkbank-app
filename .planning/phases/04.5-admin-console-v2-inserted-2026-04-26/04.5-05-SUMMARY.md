# Phase 04.5 Plan 05: User CRUD Migration + Hard-Delete Cascade Summary

ADMIN-12 closed end-to-end: user soft/hard delete with cascade, audit-logged in the same transaction, gated by a typed-confirmation UI in the admin console, and pinned by 12 backend integration assertions plus 10 admin vitest assertions. The Plan-1 Migration A schema FK strategy worked as documented — peer CardTrade rows survive with their FK nullified, historical AuditLog rows where actorId pointed to the deleted user survive as actor-tombstones with actorId=null, owned data cascades atomically.

## What Shipped

### ADMIN-12 — User soft/hard delete with cascade + typed-confirmation UI

**Backend (`backend/src/routes/admin/users.js`):**
- New endpoint `DELETE /api/admin/users/:id?mode=soft|hard`. Mode validated via `reqValidator(adminUserHardDeleteSchema, 'query')` with Zod default `'soft'`, enum `['soft','hard']`, optional `confirmPhone` (UI-side dead-man-switch only — backend does not enforce phone match).
- Soft-delete (default): inside `auditLog.withAudit` tx, `tx.user.update` sets `deletedAt = now()`. Pre-update guard rejects already-archived users with 409 `USER_ALREADY_DELETED`. Audit row `USER_SOFT_DELETE` with actorId=admin, before/after payload diff. Idempotent rejection, not silent re-stamp.
- Hard-delete: self-delete guard runs BEFORE the tx opens — `if (req.userId === id) throw USER_SELF_DELETE_FORBIDDEN`. Inside `withAudit` tx, captures `before` (id/name/phone/status), then `tx.user.delete` lets Plan-1 Migration A cascade FKs do the heavy lifting (BankAccount/BankCard/UserCard/Deck/Transaction/Notification/UserQuest/Subscription/SpendingLimit all `onDelete: Cascade`; CardTrade.from/toUserId `SetNull`; AuditLog.actor `SetNull`). Returns 204.
- Paged list `GET /` normalized to UI-SPEC `{items, total, page, limit}` shape. Both `?page=N` (new) and `?offset=N` (legacy) accepted; legacy `{users, total, limit, offset}` keys preserved alongside the new keys for back-compat with the existing UsersPage `data.users ?? []` reader.
- All default queries (paged list + PUT detail) filter `where: { deletedAt: null }` so soft-deleted users are excluded from admin reads (Test 4 pins the exclusion).
- requireFreshAdmin cache invalidated for both soft- and hard-deleted users.

**Admin SPA (`admin/src/App.jsx`):**
- UsersPage extended with two new row CTAs alongside `Изменить`:
  - `Архивировать` (yellow secondary) — opens standard ConfirmDialog with locked Russian copy `Пользователь будет архивирован. Вход будет запрещён, данные сохранятся.` and confirm label `Архивировать пользователя`. Fires `DELETE /admin/users/${id}?mode=soft`. Toast `Пользователь архивирован` on success.
  - `Удалить навсегда` (red destructive) — opens ConfirmDialog with `requireTypedConfirmation={user.phone}` and `typedPrompt={`Введите номер телефона ${user.phone} для подтверждения:`}`. Locked Russian copy `Будут удалены: счета, банковские карты, карты-коллекции, колоды, refresh-токены. История обменов сохранится с обнулённой ссылкой. Действие необратимо.` Disabled when `user.id === currentAdminId` (self-delete UI guard, mirrors backend gate). Toast `Пользователь удалён` on success.
- `decodeJwtUserId(token)` inline helper exposes the deleting admin's id (UI-only; backend USER_SELF_DELETE_FORBIDDEN remains authoritative).
- Error toasts route through `toastErrorFromAppError` → admin codebook lookup → Russian copy. New codebook entries for `USER_ALREADY_DELETED` ("Пользователь уже архивирован") and `USER_SELF_DELETE_FORBIDDEN` ("Невозможно удалить самого себя") added to both `backend/src/errors/messages.js` and `admin/src/errors/codebook.js`.

## Auth-Lookup Gap (deferred follow-up)

`backend/src/routes/auth.js` `loginHandler` performs `req.prisma.user.findUnique({ where: { phone } })` with NO `deletedAt: null` filter. A soft-deleted user could still log in if they retain access to their phone+PIN. The soft-delete UI promise "Вход будет запрещён" is currently NOT enforced at the backend.

This is **out of Plan 5's scope** (the plan's `<must_haves>` line explicitly says "auth lookup hardening lives elsewhere — verify `backend/src/routes/auth.js` already filters or document the gap in 05-SUMMARY"). Filing as a Phase 4.5 follow-up:

**[GAP]** `backend/src/routes/auth.js:61` — `findUnique({ where: { phone } })` should be `findFirst({ where: { phone, deletedAt: null } })`. Same gap likely in `requireFreshAdmin` (which does `findUnique` on the userId from the JWT to recheck `isAdmin`). Mitigations needed: tx-level filter at both call sites + a regression test that posts /auth/login for a soft-deleted user and asserts 401.

Risk severity: medium. The hard-delete path is unaffected (the row is gone, not just tombstoned). The soft-delete UI message is misleading until this gap is closed. Tracked as a v1.0 cleanup item, not a v1.1 deferral — should land before Phase 8.

## Deviations from Plan

### Auto-fixed (Rules 1-3)

1. **[Rule 3 — Blocking] Test seed schema mismatches.** Plan's <action> step seed shape used a few model field names that don't exist in `backend/prisma/schema.prisma`:
   - `UserCard.currentHealth` → actual column is `health` (no `current` prefix). **Fixed in test seed.**
   - `DeckCard.position` → actual column is `slotIndex`. **Fixed in test seed.**
   - `CardTrade.fromUserCardId` → no such column; the asset side is `offeredCardId` (a UserCard.id). **Fixed in test seed.**
   - `Notification.message + Notification.type` → actual columns are `body` (no `message`) and there's no `type` column. **Fixed in test seed.**
   - `SpendingLimit.amount` → actual column is `limitAmount`. **Fixed in test seed.**
   - `Transaction.type` enum values are `PURCHASE/TRANSFER_IN/TRANSFER_OUT/TOPUP/PAYMENT/SUBSCRIPTION/ADMIN_ADJUSTMENT` — `'TRANSFER'` and `'DEPOSIT'` from the plan prose are not valid. **Fixed test seed to use TRANSFER_OUT/TOPUP/PAYMENT.**
   - `UserCard` has `@@unique([userId, collectionCardId])` so the target's two UserCards needed two distinct templates. **Fixed by seeding a second CollectionCard (cc2).**

   None of these are bugs in this plan's implementation — they're plan-prose vs schema drift caught while writing the seed. Documented for plan-checker accuracy.

2. **[Rule 2 — Auto-add] requireFreshAdmin cache invalidation on soft-delete.** Plan-prose only required invalidation on hard-delete; I added it to soft-delete too because a soft-deleted admin should lose fresh-admin claim within ≤5 min. The auth-lookup gap (above) means this is currently the only mechanism limiting a soft-deleted admin's session window.

3. **[Rule 2 — Auto-add] PUT /:id handler filters deletedAt:null.** Plan's Test 8 asserts the contract; the existing PUT handler did `findUnique({ id })` with no filter. Switched to `findFirst({ id, deletedAt: null })` so soft-deleted users return 404 on update.

### Architectural (Rule 4) — none

No architectural decisions surfaced. Plan-1 Migration A schema work fully covered the FK requirements; no new migration was needed.
