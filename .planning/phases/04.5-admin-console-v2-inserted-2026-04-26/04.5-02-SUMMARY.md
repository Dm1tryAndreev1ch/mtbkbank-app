
### ADMIN-02 Transactions (`backend/src/routes/admin/transactions.js`)

```
GET   /api/admin/transactions         paged search (q/userId/accountId/type/status/from/to)
POST  /api/admin/transactions/:id/reverse        audit: TRANSACTION_REVERSE
POST  /api/admin/transactions/simulate           (Plan-1 carry-over)
```

The `/reverse` endpoint creates a compensating Transaction with opposite
sender/receiver, unwinds both account balances, sets
`original.reversedById = compensator.id` and flips `original.status` to
`'reversed'`. Reversibility + idempotency guards:

- **Idempotency** (`reversedById` guard): a second reverse attempt against an
  already-reversed transaction returns 409 `TRANSACTION_ALREADY_REVERSED`.
- **Race safety**: two concurrent calls collide on the UNIQUE
  `Transaction_reversedById_key` index → `P2002` is caught and translated to
  the same 409.
- **Reversibility** (`status` guard): only `status='completed'` rows can be
  reversed; otherwise 409 `TRANSACTION_NOT_REVERSIBLE`.
- **Guard ordering** (Rule-1 bug fix): the `reversedById` check runs BEFORE
  the `status` check, otherwise the second reverse attempt would surface the
  less specific NOT_REVERSIBLE message.

### Migration B (`backend/prisma/migrations/20260427_admin_transaction_reversed_by/`)

```sql
ALTER TABLE "Transaction" ADD COLUMN "reversedById" TEXT;
CREATE UNIQUE INDEX "Transaction_reversedById_key" ON "Transaction"("reversedById");
ALTER TABLE "Transaction"
  ADD CONSTRAINT "Transaction_reversedById_fkey"
  FOREIGN KEY ("reversedById") REFERENCES "Transaction"("id")
  ON DELETE SET NULL ON UPDATE NO ACTION;
```

Additive nullable column — safe online apply; default Prisma transaction is
fine (no `-- prisma-disable-transaction` needed). Applied to the dev DB
(`localhost:5432/mtbbank`) during execution via `prisma migrate deploy`.
Force-added (`git add -f`) because the repo `.gitignore` globally ignores
`**/migration.sql`.

### ADMIN-08 Payments (`backend/src/routes/admin/payments.js`)

```
GET   /api/admin/payments              paged Transaction WHERE type='PAYMENT'
POST  /api/admin/payments/:id/status   audit: PAYMENT_STATUS_OVERRIDE
```

**Decision**: there is no Prisma `Payment` model — payments are
`Transaction` rows with `type='PAYMENT'` (see existing
`backend/src/routes/payments.js`). The admin endpoint is therefore a
type-scoped view of Transaction; the status override updates a Transaction
row, refusing non-PAYMENT rows with 404.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] Generic 500 swallowed AppError in /transactions/transfer + /transfer-own**

- **Found during:** ADMIN-01 verification (`admin-accounts.test.js` `frozen account blocks debit on /api/transactions/transfer with 423 ACCOUNT_FROZEN`)
- **Issue:** Plan 1 wired `throw new AppError('ACCOUNT_FROZEN', 423)` in the debit-path of both `/transfer` and `/transfer-own` (`backend/src/routes/transactions.js:180` and `:343`), but the surrounding `catch` blocks returned a generic `res.status(500).json({error: 'Ошибка сервера'})` for ANY thrown error, swallowing the AppError. The frozen-account contract was therefore unverifiable in tests until this fix.
- **Fix:** Added `if (err && err.isAppError) return res.status(err.status || 500).json({error: err.code, message: err.message});` before the 500 fallback in both catch blocks.
- **Files modified:** `backend/src/routes/transactions.js`
- **Commit:** `e3e008c`

**2. [Rule 1 — Bug] Reverse guard ordering in /admin/transactions/:id/reverse**

- **Found during:** ADMIN-02 verification (`admin-transactions.test.js` `POST /:id/reverse on already-reversed tx returns 409 TRANSACTION_ALREADY_REVERSED`)
- **Issue:** A successful reverse flips `original.status` to `'reversed'`, so a SECOND reverse attempt would hit the `status !== 'completed'` guard FIRST and return `TRANSACTION_NOT_REVERSIBLE` instead of the more specific `TRANSACTION_ALREADY_REVERSED`. The P2002 catch handles the race window, but for the sequential same-thread case the wrong error code surfaced.
- **Fix:** Reordered the in-tx checks so `reversedById` is checked before `status`.
- **Files modified:** `backend/src/routes/admin/transactions.js`
- **Commit:** `e3e008c`

**3. [Rule 3 — Blocking] adminSubscriptionCreateSchema under-specified**

- **Found during:** ADMIN-09 implementation
- **Issue:** Plan 1's scaffold of `adminSubscriptionCreateSchema` only declared `{userId, name, amount, period?}`. But the underlying Prisma `Subscription` model REQUIRES `icon` and `nextPayment` (both `NOT NULL`), and `amount` is `Float` (Plan 1 used `z.number().int()`). Without these fields the route handler can't satisfy the Prisma `create()` invocation.
- **Fix:** Extended `adminSubscriptionCreateSchema` to include `icon` (default `'subscriptions'`), `category` (optional), `nextPayment` (datetime string optional — route falls back to `now+30d`). Widened `amount` from `int` → `number`.
- **Files modified:** `backend/src/schemas/admin.js`
- **Commit:** `0dec46b`

### Pre-existing Schema Drift (Out-of-scope; documented for orchestrator)

While running integration tests against the dev DB, I discovered that
`backend/prisma/schema.prisma` declares `Subscription.category String @default("Другое")`,
but the init migration (`20260422130817_init/migration.sql`) does not create
that column. Prisma client tries to insert the default value (`'Другое'`)
and the dev DB rejects it with `column "category" does not exist`. To
unblock test verification I ran a one-off `ALTER TABLE "Subscription" ADD
COLUMN IF NOT EXISTS "category" TEXT NOT NULL DEFAULT 'Другое'` against the
dev DB.

This drift is **pre-existing** (CONTEXT/RESEARCH/PATTERNS make no mention
of a Subscription.category migration; Plan 1 SUMMARY likewise does not
list it). It is **out-of-scope** for Plan 04.5-02. The orchestrator should
either (a) ship a tiny additive migration `20260427_admin_console_v2_cascade_b`
that adds Subscription.category formally, or (b) drop the schema field if
it was an accidental addition. The dev DB I patched will diverge from a
fresh `prisma migrate deploy` until a migration is committed — note this
during phase 4.5 final verification (Plan 6).
